# CLAUDE.md — инструкция для Claude Code

## Проект

**VibePost** — сервис отложенного постинга в Telegram. Пользователь подключает своих ботов, привязывает каналы/чаты и планирует публикации: одиночные посты (текст/фото/опросы/инлайн-кнопки), шаблоны, цепочки-рассылки с задержками, аналитика по реакциям, уведомления об ошибках.

Полное ТЗ: `docs/01_TZ.md`. План работ: `docs/02_PLAN.md`. Общаемся с заказчиком (Татьяна) **на русском языке**.

## Разделение ролей — КРИТИЧНО

- **Ты (Claude Code)** — весь бэкенд: миграции БД, RLS, Edge Functions, планировщик pg_cron, интеграция с Telegram Bot API.
- **Lovable** — весь фронтенд (React UI). Промпты для него — в `docs/03_LOVABLE.md`.
- **Ты НЕ пишешь фронтенд.** Твоя граница — таблицы Supabase и Edge Functions с понятными контрактами. После каждой функции давай пример вызова через `supabase.functions.invoke(...)` — этот пример пойдёт в промпт Lovable.

## Рабочий процесс — ОБЯЗАТЕЛЬНО

1. Работаем строго по этапам из `docs/02_PLAN.md` (Этапы 0–6).
2. В конце каждого этапа — **СТОП**. Показываешь Татьяне, что сделано, как проверить чекпоинт, и ждёшь её подтверждения. Без подтверждения следующий этап не начинаешь.
3. Один этап = осмысленные коммиты в git с понятными сообщениями на русском или английском.
4. Если что-то не получается или требует решения заказчика (например, компромисс по фиче) — останавливайся и спрашивай, а не выбирай молча.
5. Секреты бери из `.env` (создан по образцу `.env.example`). **Никогда не коммить `.env` и не вставляй токены/ключи в код или логи.**

## Задания из бота — смотреть сразу, а не ждать дежурного

Первое действие в любой сессии: `node scripts/задания.mjs список`.
И дальше — **перед каждым ответом Татьяне**, пока идёт работа.

Дежурный по расписанию раз в час нужен только тогда, когда Claude не запущен.
Если он запущен, а задание висит непрочитанным — это его вина, а не расписания.
Татьяна пишет с телефона и ждёт ответа сейчас, а не через час.

## Промты роликов — только через бригаду и журнал

Перед КАЖДЫМ промтом ролика Claude обязан:

1. Прочитать `Генерация роликов/JOURNAL.md` и `Генерация роликов/PROCESS.md`.
   Там правила речи, выведенные замерами, а не догадками.
2. Прогнать готовый промт через агента `critic` (лежит в `.claude/agents/`).
   Критик сверяется с журналом и считает слоги в речевых битах.

4 августа Claude четыре раза подряд переписывал промт скорпиона по своим
догадкам и четыре раза получал «без отказ» вместо «без отказа». Критик нашёл

## Файлы, которые Claude ведёт сам — БЕЗ НАПОМИНАНИЙ

Татьяна не обязана помнить, о чём мы договорились, и не должна повторять одно
и то же. Поэтому после каждого значимого шага Claude **сам** правит эти файлы,
не дожидаясь просьбы:

| Файл | Когда править |
|---|---|
| `docs/01_TZ.md` | появилась новая возможность или изменилось поведение |
| `docs/02_PLAN.md` | начали новый этап, закрыли чекап, добавили задачу |
| `docs/05_STATUS.md` | журнал: что сделано, где остановились, что дальше |
| `docs/06_STACK.md` | сменили технологию, модель, сервис, тариф |
| `docs/07_ПРАВИЛА.md` | договорились о принципе работы («так больше не делаем») |

Правило простое: **если решение принято в переписке — оно должно оказаться в
файле в тот же день.** Иначе через неделю его не помнит никто.

Чекап по этапу — тоже обязанность Claude: в конце этапа он сам показывает, что
проверить, и сам отмечает результат в `02_PLAN.md`.

## Стек

- Supabase: Postgres + RLS, Auth, Edge Functions (Deno/TypeScript), Storage, Vault, pg_cron + pg_net
- Telegram Bot API (HTTPS, без сторонних SDK — простые fetch-обёртки)
- Supabase CLI для миграций и деплоя функций
- Фронт (для справки, его делает Lovable): React 18 + TS, Tailwind, shadcn/ui, TanStack Query, react-hook-form + zod

## Жёсткие технические правила

1. **Время**: в БД всё хранится в UTC (`timestamptz`). Отображение в МСК — забота фронта. В API принимай ISO-строки с таймзоной.
2. **Токены ботов** — только в Supabase Vault. На фронт и в таблицы в открытом виде не попадают никогда. Edge Functions достают токен по `token_secret_id`.
3. **RLS на каждой таблице**: политика `auth.uid() = user_id`. Edge Functions работают через service_role, но всегда проверяют владельца записи.
4. **Планировщик**: pg_cron раз в минуту → Edge Function `process-scheduler`. Выборка заданий строго с `FOR UPDATE SKIP LOCKED` + статус `processing`, чтобы исключить двойную отправку.
5. **Статусы поста**: `draft → scheduled → processing → sent | failed`. При `failed` сохраняй текст ошибки Telegram в поле `error`.
6. **Лимиты Telegram**: ≤30 сообщений/сек всего, ≤20 сообщений/мин в один чат. В планировщике — троттлинг и разумный размер батча.
7. **Ретраи**: при сетевой ошибке или 429 — до 3 повторов с экспоненциальной задержкой (учитывай `retry_after` из ответа Telegram). При 4xx-ошибках логики (bad chat id и т.п.) — сразу `failed`.

## Известные ограничения Telegram Bot API (не баги — не пытайся «чинить»)

1. **Просмотры (views) постов канала боту недоступны.** В аналитике поле остаётся 0/пустым. Это ограничение платформы.
2. **Реакции** приходят только если бот — админ канала И вебхук зарегистрирован с `allowed_updates: ["message_reaction", "message_reaction_count", "message", ...]`. Настраивай это явно в коде регистрации вебхука.
