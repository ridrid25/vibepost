# ingest-video

Приёмник готовых роликов от внешнего конвейера (Veo и т.п.). Кладёт видеофайл в
Storage и заводит запись во «Входящих» — `incoming_videos` со `status='new'`.

**В канал ничего не публикуется.** Дальше ролик разбирает бот в Telegram:
предлагает подписи и хуки, Татьяна выбирает кнопками, и только потом из этого
получается пост. Приёмник — первое звено, а не отправка.

## Кто её вызывает

Локальный конвейер озвучки из репозитория `vibepost-video`
(`scripts/lib/deliver.mjs` → `scripts/lib/vibepost.mjs`). Вызов включается,
только если в его `.env` заданы `VIBEPOST_INGEST_URL` и ключ.

Второй путь во «Входящие» — функция `video-from-bot`: ролик, присланный боту
прямо в Telegram. Она пишет в ту же таблицу с тем же `status='new'`, так что
дальше оба пути идут одинаково.

## Контракт

`POST` `multipart/form-data` на
`https://<project>.supabase.co/functions/v1/ingest-video`

Заголовок `X-Ingest-Secret: <секрет>` — обязателен.

| Поле | Обяз. | Что это |
| --- | --- | --- |
| `file` | **да** | видеофайл; расширение берётся из имени, по умолчанию `mp4` |
| `name` | нет | короткое имя ролика, до 200 знаков |
| `prompt` | нет | промт, которым ролик сгенерирован, до 4000 знаков |
| `source` | нет | откуда пришёл (`veo`, `flow`…), до 200 знаков |
| `caption` | нет | заготовка подписи, до 1024 знаков |

Поле файла называется **`file`**, а не `video` — на этом легко ошибиться.

Ответ `200`: `{ id, video_url }`.

| Код | Когда |
| --- | --- |
| `400` | тело не `multipart/form-data` или нет поля `file` |
| `403` | заголовок `X-Ingest-Secret` отсутствует или не совпал |
| `405` | метод не `POST` |
| `500` | не удалось загрузить файл, или владелец не настроен в Vault |

Если запись в таблицу не удалась, залитый файл удаляется — мусор в Storage
не копится.

## Авторизация и секреты

Функция развёрнута с `verify_jwt=false`: её зовёт внешняя система, у которой
нет пользовательской сессии Supabase. Поэтому проверка своя — по секретному
заголовку, а не по JWT.

Оба значения лежат в Vault и в коде не встречаются:

| Секрет | Что |
| --- | --- |
| `vibepost_ingest_secret` | значение для заголовка `X-Ingest-Secret` |
| `vibepost_ingest_owner` | `user_id` владельца, под которым создаются записи |

Читаются через `get_ingest_secret()` / `get_ingest_owner()` — обе `security
definer` и доступны только `service_role`. Задаются один раз:

```sql
select store_ingest_config('<секрет>', '<user_id владельца>'::uuid);
```

Внутри функции оба значения кешируются в памяти воркера. Сменили секрет —
передеплойте функцию, иначе старое значение будет жить до перезапуска.

## Куда попадает файл

Бакет `post-photos`, путь `<user_id>/incoming/<uuid>.<ext>`. Ссылка берётся
через `getPublicUrl` — то есть **публичная**: кто знает адрес, тот откроет
ролик без авторизации. Для черновиков это осознанный размен ради простоты
предпросмотра в боте, но выкладывать такие ссылки наружу не стоит.

## Что происходит дальше

Запись во `incoming_videos` живёт с полями разбора: `review`, `hook`,
`hook_options`, `caption_options`, `tag`, замеры динамики (`measure_avg`,
`measure_worst`, `measure_cuts`), пометки переделки (`rework_note`,
`rework_at`) и флаг `ready`. Заполняют их `telegram-webhook`, `idea-button`,
`hook-options` — приёмник ничего этого не трогает, он только принимает.

Статусы: `new` → `scheduled` (ролик ушёл в пост) либо `dismissed` (отклонён).

## Деплой

```
supabase functions deploy ingest-video --no-verify-jwt
```

Флаг обязателен: без него Supabase начнёт требовать JWT и внешний конвейер
получит `401` ещё до кода функции.

Отдельных переменных окружения не нужно — используются штатные
`SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY`.

## Проверка живьём

```
curl -i -X POST "https://<project>.supabase.co/functions/v1/ingest-video" \
  -H "X-Ingest-Secret: <секрет>" \
  -F "file=@ролик.mp4" \
  -F "name=проверка-приёмника" \
  -F "source=curl"
```

Ждём `200` и `{ "id": ..., "video_url": ... }`, а во «Входящих» — новую запись.

## Известное расхождение (на 11.08.2026)

Вызывающая сторона в `vibepost-video` написана под **прежний** контракт этой
функции: она шлёт файл в поле `video` и авторизуется заголовком
`Authorization: Bearer <service_role>`, без `X-Ingest-Secret`. Функция такой
запрос отклоняет с `403`.

Ошибка проглатывается: в `deliver.mjs` вызов обёрнут в `try/catch` и пишет в
лог строчку «VibePost не отправлен», после чего конвейер продолжает работу.
Поэтому со стороны выглядит так, будто доставка просто не настроена.

Чинить нужно вызывающую сторону — переименовать поле в `file` и слать
`X-Ingest-Secret`. Здесь это записано, чтобы следующий читатель не начал
править работающий приёмник под сломанного клиента.
