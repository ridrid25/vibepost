# ТЗ: VibePost — отложенный постинг в Telegram

## 1. Назначение

SaaS-сервис для планирования публикаций в Telegram-каналы и чаты:

- подключение своих ботов (токен от BotFather) и привязка каналов/чатов;
- отложенные посты на дату/время: текст, фото с подписью, опросы, инлайн-кнопки, тихая отправка, отключение превью ссылок;
- шаблоны сообщений с переиспользованием;
- **цепочки** — последовательности постов с задержками (drip-рассылки): прогресс, пауза, возобновление;
- аналитика (реакции по постам; просмотры — см. ограничения);
- уведомления об ошибках отправки в личный Telegram владельца.

Часовой пояс интерфейса по умолчанию — Europe/Moscow. Хранение — всегда UTC.

## 2. Стек

| Слой | Технология |
|---|---|
| БД | Supabase Postgres + Row Level Security |
| Аутентификация | Supabase Auth (email/пароль) |
| Серверная логика | Supabase Edge Functions (Deno/TS) |
| Планировщик | pg_cron (раз в минуту) + pg_net → Edge Function |
| Секреты | Supabase Vault (токены ботов) |
| Файлы | Supabase Storage (фото постов) |
| Интеграция | Telegram Bot API (fetch, без SDK) |
| Фронтенд (Lovable) | React 18 + TS, Vite, Tailwind, shadcn/ui, TanStack Query, react-hook-form + zod |

## 3. Схема данных (11 таблиц)

```
profiles
  id uuid PK → auth.users
  timezone text default 'Europe/Moscow'
  error_notify_tg_id text          -- Telegram ID для уведомлений об ошибках
  error_notify_bot_id uuid null    -- каким ботом слать уведомления
  created_at timestamptz

bots
  id uuid PK, user_id uuid
  name text, username text
  token_secret_id uuid             -- ссылка на Vault, токен в открытом виде НЕ хранится
  is_active bool default true
  created_at

chats
  id uuid PK, user_id, bot_id → bots
  title text
  telegram_chat_id text            -- например -1001234567890 или 252467162
  type text check in ('private','channel','group')
  created_at

message_templates
  id uuid PK, user_id
  name text
  format text check in ('text','photo','poll')
  text text null
  photo_url text null
  poll_question text null
  poll_options jsonb null          -- ["Вариант 1","Вариант 2"]
  poll_anonymous bool default true
  inline_buttons jsonb null        -- [[{"text":"...","url":"..."}], ...]
  is_silent bool default false
  disable_link_preview bool default false
  created_at

posts
  id uuid PK, user_id, bot_id, chat_id
  template_id uuid null
  format / text / photo_url / poll_question / poll_options / poll_anonymous
  inline_buttons / is_silent / disable_link_preview   -- те же поля, что в шаблоне
  scheduled_at timestamptz         -- UTC
  status text check in ('draft','scheduled','processing','sent','failed') default 'scheduled'
  tg_message_id bigint null
  error text null
  retry_count int default 0
  sent_at timestamptz null
  created_at

message_chains
  id uuid PK, user_id, name text, created_at

chain_steps
  id uuid PK, chain_id → message_chains
  position int
  delay_minutes int                -- задержка от старта цепочки
  template_id uuid null            -- либо инлайн-контент (те же поля, что в шаблоне)
  format / text / photo_url / ... (nullable)
  created_at

active_chains
  id uuid PK, user_id, chain_id, bot_id, chat_id
  status text check in ('running','paused','done') default 'running'
  started_at timestamptz
  paused_at timestamptz null
  created_at

active_chain_steps
  id uuid PK, active_chain_id → active_chains, step_id → chain_steps
  scheduled_at timestamptz
  status text check in ('scheduled','processing','sent','failed','skipped')
  tg_message_id bigint null, error text null, sent_at timestamptz null

post_analytics
  id uuid PK
  post_id uuid null, active_chain_step_id uuid null
  chat_id uuid, tg_message_id bigint
  views int default 0              -- см. ограничение: Bot API просмотры не отдаёт
  reactions jsonb default '{}'     -- {"👍": 3, "🔥": 1}
  reactions_count int default 0
  updated_at

notifications
  id uuid PK, user_id
  type text                        -- 'post_failed' | 'chain_failed' | ...
  message text
  is_read bool default false
  created_at
```

Индексы: `posts (status, scheduled_at)`, `active_chain_steps (status, scheduled_at)`, `post_analytics (chat_id, tg_message_id)`.

RLS: на всех таблицах включён, политика `auth.uid() = user_id` (для дочерних таблиц цепочек — через join к родителю или денормализованный `user_id`).

Триггер: при регистрации пользователя (insert в `auth.users`) автоматически создавать строку в `profiles`.

## 4. Edge Functions (контракты)

### validate-bot
Вход: `{ token, name }` (JWT пользователя обязателен).
Логика: `getMe` к Telegram → если ок, сохранить токен в Vault, создать запись в `bots`, вернуть `{ id, username, name }`. Если токен неверный — 400 с текстом ошибки.

### resolve-chat
Вход: `{ bot_id, telegram_chat_id }`.
Логика: `getChat` через токен бота → проверить доступ, определить `type` и `title`, создать запись в `chats`. Ошибка, если бот не имеет доступа к чату.

### send-post (внутренний модуль, используется планировщиком)
По `format`:
- `text` → `sendMessage` (`text`, `link_preview_options.is_disabled`, `disable_notification`, `reply_markup`)
- `photo` → `sendPhoto` (`photo`, `caption`, остальное аналогично)
- `poll` → `sendPoll` (`question`, `options`, `is_anonymous`)
- инлайн-кнопки → `reply_markup: { inline_keyboard: [...] }`
Возвращает `message_id` Telegram. Ошибки Telegram пробрасываются наверх с текстом.

### process-scheduler (вызывается pg_cron раз в минуту)
1. Выбрать до N (например, 25) записей из `posts` и `active_chain_steps` где `status='scheduled' and scheduled_at <= now()` **с `FOR UPDATE SKIP LOCKED`**, сразу проставить `processing`.
2. Для каждой — достать токен бота из Vault, отправить через send-post с троттлингом.
3. Успех → `sent`, `tg_message_id`, `sent_at`, создать строку в `post_analytics`.
4. Ошибка сети/429 → ретрай (до 3, с учётом `retry_after`); иначе `failed` + `error` + вызов notify-error.
5. Для шагов цепочек: если все шаги `sent` — у `active_chains` статус `done`. Если цепочка `paused` — шаги не отправлять.

### activate-chain
Вход: `{ chain_id, bot_id, chat_id }`.
Создаёт `active_chains (running, started_at=now())` и `active_chain_steps` с `scheduled_at = started_at + delay_minutes` каждого шага.

Пауза/возобновление (`toggle-chain`, можно частью той же функции):
- пауза: `status='paused'`, `paused_at=now()`;
- возобновление: сдвинуть `scheduled_at` всех неотправленных шагов на `now() - paused_at`, вернуть `running`.

### telegram-webhook
Регистрация: `setWebhook` с `allowed_updates: ["message","message_reaction","message_reaction_count"]` и секретным токеном (`secret_header`).
Приём `message_reaction_count` / `message_reaction` → обновить `reactions`, `reactions_count` в `post_analytics` по `(chat, message_id)`.
Проверять секретный заголовок, чужие запросы отбрасывать с 403.

### notify-error
Вход: `{ user_id, type, message }`.
Отправить `sendMessage` на `profiles.error_notify_tg_id` через бота `error_notify_bot_id` (если настроены) + запись в `notifications`.

## 5. Планировщик (SQL)

```sql
select cron.schedule('vibepost-scheduler', '* * * * *', $$
  select net.http_post(
    url := 'https://<PROJECT_REF>.functions.supabase.co/process-scheduler',
    headers := jsonb_build_object(
      'Content-Type','application/json',
      'Authorization','Bearer ' || '<SERVICE_ROLE_KEY_ИЗ_VAULT>'
    ),
    body := '{}'::jsonb
  );
$$);
```
Ключ подставлять из Vault/настроек, не хардкодить в миграции.

## 6. Ограничения и риски (зафиксировано)

1. **Просмотры каналов** через Bot API недоступны — в аналитике поле остаётся 0. Возможные будущие обходы (MTProto-клиент) — вне скоупа MVP.
2. **Реакции** требуют: бот — админ канала, вебхук с нужными `allowed_updates`.
3. **Точность расписания** — 1 минута (pg_cron).
4. **Лимиты Telegram**: ~30 msg/сек всего, ~20 msg/мин в один чат → троттлинг в планировщике.
5. **Безопасность**: токены только в Vault; RLS везде; вебхук защищён секретом; service_role только внутри Edge Functions.

## 7. Критерий готовности MVP

Пользователь регистрируется, добавляет бота и канал, планирует пост на +2 минуты — пост реально приходит в канал; создаёт шаблон и цепочку из 2 шагов — оба шага приходят по времени; реакция на пост появляется в аналитике; при неверном Chat ID приходит уведомление об ошибке в личку.

## 8. YouTube Shorts field trial V0.1

- Владелец выбирает `TikTok` или `YouTube Shorts` в существующем Telegram-боте; выбор хранится в `profiles.target_platform` и переживает restart.
- Для YouTube Shorts `suggest-ideas` получает небольшой live-набор YouTube Data API и передаёт в существующие карточки только оригинальные адаптации причинной механики. TikTok сохраняет прежний production flow.
- Перед созданием YouTube-карточек `suggest-ideas` обязан сверить кандидатов со всей сохранённой YouTube-историей владельца. Совпадение `slug`, хука, реплики или scenario prompt запрещает сохранение и отправку; при отсутствии новой пятёрки старые карточки не используются как fallback.
- Маршрут `🖐 Сделаю сама` остаётся ручным: фабрика возвращает JSON prompt в Telegram, владелец бесплатно генерирует ролик и присылает его тому же боту.
- Review остаётся advisory; для reference-driven ролика дополнительно фиксируется `causal_pattern_preserved`, а окончательное решение принимает владелец.
- Сущность `chats` и планировщик Telegram-specific. YouTube upload/OAuth provider отсутствует, поэтому публикация YouTube в V0.1 ручная и не должна обозначаться как автоматическая.
