# План работ: этапы и чекапы

## Правила процесса

1. Каждый этап заканчивается **чекапом** — живой проверкой, которую Татьяна подтверждает словами «принято, дальше».
2. Claude Code **не начинает следующий этап без подтверждения**.
3. Если на чекапе что-то не работает — этап дорабатывается, пока чекап не пройдёт.
4. Чекап — это всегда реальное действие (сообщение пришло в Telegram, запись появилась в БД), а не «код написан».
5. Задачи Lovable из этапа можно вести параллельно, как только готовы таблицы/функции этого этапа (промпты — в `docs/03_LOVABLE.md`).

---

## Этап 0 — Фундамент: проект + полная схема БД

Решение: миграции создаём **сразу все**, а не по кусочкам — схема согласована, а Lovable без таблиц не может строить UI.

**Татьяна (до старта):** выполнить чеклист из `docs/04_SETUP.md` (Supabase-проект, ключи, тестовый бот, тестовый канал, `.env`).

**Claude Code:**
1. Инициализировать репозиторий, структуру из CLAUDE.md, `supabase init`, привязка к проекту (`supabase link`).
2. Миграции: все 11 таблиц + check-констрейнты + индексы + RLS-политики + триггер автосоздания `profiles`.
3. Применить миграции (`supabase db push`), включить расширения `pg_cron`, `pg_net`.
4. Мини-скрипт проверки RLS (анонимный клиент не видит чужие данные).

**✅ Чекап 0:** в Supabase Dashboard видны все 11 таблиц; регистрация тестового пользователя создаёт строку в `profiles`; RLS-проверка проходит.

## Этап 1 — Боты и чаты

**Claude Code:**
1. Edge Function `validate-bot`: `getMe` → Vault → запись в `bots`.
2. Edge Function `resolve-chat`: `getChat` → запись в `chats`.
3. Деплой функций, примеры вызова `supabase.functions.invoke(...)` для Lovable.

**Lovable (параллельно):** страницы логина/регистрации, каркас навигации, страница «Настройки» с формой добавления бота и привязкой чатов.

**✅ Чекап 1:** через curl или UI добавляем реальный токен тестового бота → бот валидируется, появляется в `bots`, токен лежит в Vault (в таблице его нет). Привязываем тестовый канал → запись в `chats`.

## Этап 2 — Ядро: одиночные посты по расписанию

**Claude Code:**
1. Модуль `send-post`: sendMessage / sendPhoto / sendPoll + inline_keyboard + тихая отправка + отключение превью.
2. Edge Function `process-scheduler` с `FOR UPDATE SKIP LOCKED`, троттлингом и ретраями.
3. Регистрация задачи pg_cron (раз в минуту).
4. Тест: вставить пост со `scheduled_at = now() + 2 мин` напрямую в БД.

**Lovable:** страница «Все посты» (календарь/список, фильтр по чату), модалка «Новый пост» (все поля, дата/время в МСК → UTC).

**✅ Чекап 2 (главный в проекте):** пост, запланированный на +2 минуты, **реально приходит** в тестовый канал; статус в БД `scheduled → sent`, `tg_message_id` заполнен. Проверяем все форматы: текст, фото, опрос, инлайн-кнопки, тихий пост.

## Этап 3 — Шаблоны

**Claude Code:** CRUD-логики на бэке почти нет (RLS-таблица уже есть) — проверить политику, при необходимости добавить копирование шаблона в пост на уровне SQL/функции.

**Lovable:** страница «Шаблоны» (таблица, создание/редактирование/копирование/удаление), выбор шаблона в модалке «Новый пост» с автозаполнением полей.

**✅ Чекап 3:** создаём шаблон → создаём из него пост в пару кликов → пост приходит в канал.

## Этап 4 — Цепочки

**Claude Code:**
1. Edge Function `activate-chain` (+ пауза/возобновление со сдвигом времени).
2. Обработка `active_chain_steps` в `process-scheduler`, статус `done` у цепочки.

**Lovable:** страница «Цепочки»: блок активных (прогресс X/Y, пауза/возобновить), блок шаблонов цепочек (шаги, задержки, кнопка «Запуск» с выбором бота и чата).

**✅ Чекап 4:** цепочка из 2 шагов (задержки 2 и 4 минуты) отправляет оба поста вовремя; пауза после первого шага останавливает второй; возобновление досылает его с корректным сдвигом.

---

## Этап 5 — Аналитика

**Claude Code:**
1. Edge Function `telegram-webhook` + регистрация `setWebhook` с `allowed_updates` и секретом.
2. Обновление `post_analytics` по реакциям.

**Татьяна:** убедиться, что бот — админ тестового канала.

**Lovable:** страница «Аналитика» — топ постов (текст, тип, чат, просмотры, реакции).

**✅ Чекап 5:** ставим реакцию на пост в канале → через несколько секунд `reactions_count` в БД и в UI увеличивается. Просмотры показывают 0 — это ожидаемо (ограничение Bot API), фиксируем как норму.

---

## Этап 6 — Уведомления об ошибках и полировка

**Claude Code:**
1. Edge Function `notify-error` + вызов из планировщика при `failed`.
2. Прогон по краевым случаям: неверный chat_id, отозванный токен, 429.

**Lovable:** секция «Уведомления об ошибках» в настройках (Telegram ID), колокольчик непрочитанных из `notifications`.

**✅ Чекап 6 (финальный):** намеренно планируем пост с неверным Chat ID → пост уходит в `failed`, в личный Telegram приходит уведомление, в UI появляется непрочитанное. После этого — полный прогон сценария MVP из ТЗ (раздел 7).
